Case Study · 2026.07 – 至今 · 早期科技公司

内部 AI
工具与治理体系

把 AI 的供给、介入与采纳，变成可以运行的系统。产品经理实习生（AI-Native 产品与内部工具方向）。本页保留真实的判断结构，但公司身份、组织、实现与结果信息均已三次脱敏。

Problem

公司开始使用 AI，
但供给、介入与采纳都未被定义。

模型能力的使用缺少统一边界，Agent 进入工作流的方式尚未定义，组织也没有可靠的使用事实。这不是一个工具缺口，而是供给、介入与采纳三个层面必须同时被定义的问题。

Definition

不是一个平台，
是三个必须同时成立的定义。

我没有把问题收敛成“做一个内部工具”，而是把它拆成三层：公司如何供应 AI，Agent 如何进入工作流，以及组织如何形成真实采纳。三层互相约束：供给没有边界会失控，介入没有闭环会失责，采纳没有事实基线会变成口号。

Supply

决策与执行分层。 控制面负责身份、权限、预算与审计；执行层只执行已经做出的策略。

Intervention

先判断介入形式。 对每个工作流区分替代执行、辅助生成与结果校验，并明确人保留在哪个闭环节点。

Adoption

把采纳当作产品问题。 建立使用事实、能力准备度与可复用知识的沉淀路径，让供给对应真实需求。

Decision Archive

真正稀缺的产出，
是五次有代价的判断。

实现细节大多不能公开，判断可以。以下五个决策分别记录当时的处境、约束、决定与代价；没有代价的决定，不值得被包装成案例。

Decision 01

从“能不能修”转向“值不值得继续投入”

处境
组织已有一项持续投入的多 Agent 协作方向，最自然的动作是继续修补。
约束
我不是最终决策者，只能提供足以改变投资判断的可复现证据。
判断
我没有把讨论停在代码质量，而是构造协作主体相互等待的可复现场景，证明缺少确定性调度时会出现无法检测、也没有恢复路径的语义死锁；再叠加既有实现的结构性风险，建议重估继续投入的边际收益。结论被采纳，这条方向停止投入。
代价
证据在并行工作中逐步积累；若先定义“什么证据足以下结论”，可以更早收口。

Decision 02

不自己写：先找到值得改造的基础设施

处境
交付窗口短、工作线并行，任何一条从零自研都会挤占关键判断与验收。
约束
团队没有余量长期维护新轮子，“先可用”和“架构完美”在这个窗口里冲突。
判断
默认先找现有实现，再用三条筛子判断：它是否扛掉最不值得自写的部分；改动集中在边界层还是核心层；它的隐含身份与权限假设是否适合多人场景。面向对话与能力共享的交付均复用既有基础设施，并提前写下退役条件。
代价
过渡件往往比计划活得更久；fork 之后，上游更新也不再自动获得。

Decision 03

先画边界，再写功能

处境
统一调用入口要兼容多类客户端与上游通路，早期又因权限边界后补发生返工。
约束
通用中间格式会损失语义；外部身份协议的字段也不归我们控制。
判断
把协议类型定义为凭证创建时确定、之后不可变的属性，让转换路径彼此独立并保持语义；同时强制外部身份声明经过显式映射，再进入内部权限模型。边界依据是所有权与变更速率，而不是今天的数据是否刚好一致。
代价
切换协议必须更换凭证，前期也多出一层看似冗余的映射；这是用灵活性换确定性。

Decision 04

不为能力共享再建一个后台

处境
组织需要可配置、可共享、有版本且可审计的 Agent 能力机制。
约束
团队没有余量维护新的管理后台，既有版本协作基础设施已经承载权限与审计。
判断
直接复用已有平台：权限沿用现有体系，提交历史提供审计，差异与评审管理变更，回滚也使用团队熟悉的动作。产品形态服从已有基建，而不是为一张更漂亮的界面复制整套治理能力。
代价
非技术同事必须面对版本协作的心智模型。模板和薄封装只能缓解，不能消除——这是全页最有争议的取舍。

Decision 05

先建立事实，再谈推行

处境
一种常见判断是：模型继续增强后，体验与采纳问题会自然减弱。
约束
我不能靠立场赢得讨论，也不能让一次宣讲替代真实使用证据。
判断
推动使用基线调研，按具体工具拆分频率、分别评价不同 AI 角色，并避免让临时检索替代真实经验。结果显示阻塞采纳的核心不是模型上限，而是稳定性、上下文连续性、工作流连接与概念理解。我据此把 enablement 从“推广活动”重定义为供需对齐机制。
代价
先调研、后演示放慢了短期推进节奏；第一次讨论也没有可立即宣布的成果。

Process

规格的精度，
就是产品的精度。

我的工作路径是需求调研 → 规格与实体关系 → 任务拆解 → Coding Agent 实现，再由我负责变更管理、测试范围、回归与验收。与工程侧按领域所有权分工，而不是按页面或功能切割责任。这段实习里我写的代码不多，写的 spec 很多；这不是角色限制，而是 Agent 参与开发后最重要的产品控制面。

Outcome

结果不只是一组数字，
也是不同的交付状态。

多个跨职能工作流完成试点并进入使用；更重要的是，交付状态被明确区分为已交付、过渡期、开发中、讨论中与停止投入。本页不公开精确效率数字，以避免由样本规模、流程类型与时间窗口反推组织信息。

统一调用边界与权限设计已交付
协作入口与执行 Agent 的连接层已交付
重复信息处理工作流已交付
基于现有实现改造的过渡工具已交付 · 待退役
可复用 Agent 能力的配置与共享开发中
能力准备度与采纳机制讨论中
自研多 Agent 协作方向已停止投入

Retrospective

边界要先于功能，
调研要先于推广。

初期按“先跑起来”推进，把配额与用户组边界后补，最终造成返工：多租户系统的第一个实体不是功能，是边界。我也曾把采纳理解成“做完再去讲”，调研后才明白它首先是产品问题——没有人会为了公司在推 AI，去忍受一个会断连的工具。如果重来，组织调研会发生在第一周。
